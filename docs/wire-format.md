# Wire format — the exact bytes

This document is the authority for every byte that crosses an implementation
boundary. When it disagrees with code, one of them gets fixed.

> **Enforcement.** The rules below are load-bearing for the Rust/Swift boundary.
> Nothing here is enforced by a version bump; the shared fixtures in
> `tests/fixtures/` and the parity harness are the enforcement.

## The Five Rules

Each paid for by a real cross-implementation bug:

1. **Standard names are not wire formats.** "ISO 8601" is a family of ~20
   formats; "UUID" can be any case; "camelCase" is ambiguous across
   Pydantic/serde/Codable. For every field, write down the exact byte
   sequence — this file does.
2. **Specify the full round-trip.** Client sends → server stores → server
   returns. If ANY step changes casing, encoding, or structure, the round-trip
   breaks. Opaque pass-through fields are especially dangerous.
3. **Test nested objects at full depth.** Top-level casing gets tested
   naturally; nested objects escape scrutiny. Banshee's payloads are nested by
   nature — a pressure snapshot carries per-dimension objects, each with its own
   bands and rates — which is why the fully-populated `pressure-shrieking.json`
   fixture exists and why both languages assert on the NESTED key sets.
4. **Two implementations, one database.** Create with A, read with B, modify with
   B, read with A. This repo runs that as a day-zero gate
   (`tests/e2e/run-e2e.sh`: CLI vs raw HTTP vs MCP).
5. **Datetime acceptance must be generous.** Producers differ (Python emits 6
   fractional digits, Swift/JS emit 3, some emit 0 or numeric offsets). Decode
   all of them; encode ONLY the canonical form.

## Datetimes

- **Canonical encode** (every implementation MUST produce exactly this):
  `2026-03-17T14:30:00.123456Z` — 6 fractional digits, `T` separator, `Z`
  suffix. Reference: `rust/banshee-core/src/wire_time.rs`,
  `swift/Sources/BansheeCore/WireDate.swift`.
- **Generous decode** (every implementation MUST accept all of):

  | Producer | Example |
  |---|---|
  | canonical / Python | `2026-03-17T14:30:00.123456Z` |
  | Swift / JavaScript | `2026-03-17T14:30:00.123Z` |
  | fractionless | `2026-03-17T14:30:00Z` |
  | numeric offset | `2026-03-17T14:30:00.123456+00:00`, `…+01:00` |

- Precision: microsecond. **Producers MUST emit exactly 6 fractional digits.**
  Decoders MUST accept more (7+), but sub-microsecond fidelity is NOT guaranteed
  and MUST NOT be relied on: an implementation may round or truncate the excess
  to microseconds, and two implementations may disagree by up to 1µs on such
  out-of-spec input (Rust's integer-nanosecond backing truncates; Swift's `Date`
  is Double-backed and rounds — they cannot be made byte-identical on 7+ digits,
  and the contract does not require it). The shared fixture
  `tests/fixtures/datetime-variants.json` pins agreement for all in-spec
  (≤6-digit) variants, cross-checked by both the Rust and Swift decode suites.
- **Year is exactly 4 digits** (`\d{4}`). The last representable canonical
  instant is `9999-12-31T23:59:59.999999Z`; encoders MUST saturate there rather
  than emit a 5-digit year (a rounding carry at that boundary once produced
  `10000-…` in Swift — now clamped).
- Known trap: Foundation's `ISO8601DateFormatter`/ICU truncates fractional
  seconds to milliseconds both ways; the Swift implementation handles the
  fraction manually for this reason. Do not "simplify" it back.

**Sampling note specific to Banshee:** sample timestamps are the primary key of
almost every query in this app, and they are generated by a timer rather than by
a user action. Two samples must never collide, and a rollup bucket boundary must
be computed from the canonical UTC value — never from a local-time rendering.
Nothing in this app is allowed to store a local timestamp.

## UUIDs

- Encode: lowercase, hyphenated (`e7ae86e2-308b-444c-8a3d-cd21467ab442`).
- Decode: accept any case, both in JSON bodies and URL paths. A wrong-case UUID
  is the same resource, not a 400.

## JSON conventions

- Keys are **camelCase at every nesting depth**.
- Nullable fields are **present-as-null**, never absent: `"body": null`,
  `"closedAt": null`. **This binds the ENCODER, not just the decoder** — and
  language defaults will betray you: Swift's synthesized `Codable` uses
  `encodeIfPresent` and silently omits nil keys (the reference implementation
  shipped that bug until 2026-08-19; the fix is a hand-written `encode(to:)` with
  explicit `encodeNil`, pinned by a test that fails against the derived
  conformance). If your language "helpfully" drops nulls, write the encoder by
  hand and pin it.
- Servers reject unknown fields on write DTOs (422), so a client sending
  snake_case keys fails loudly instead of losing data (Rule 2).
- Arrays that are empty are `[]`, never `null`.
- **Numbers:** rates and ratios are JSON numbers, not strings, and are emitted at
  full `f64` precision rather than pre-rounded for display. Rounding is a
  presentation concern and belongs in the client; a pre-rounded rate cannot be
  re-aggregated into a rollup. Counts are integers.
- **Floats have a ONE-ULP tolerance across the boundary, and equality on them is
  not part of the contract.** Verified 2026-08-31, reproduced in isolation:
  `serde_json` serialises `1.1574074074074077e-5` correctly as
  `0.000011574074074074077` and parses it back as `1.1574074074074075e-5` — one
  unit in the last place lower. So a decoded float may differ from the encoded one
  in its final bit, and **no consumer may compare a wire float with `==`.**
  Compare with a relative epsilon.

  This is the same shape as the datetime tolerance above (Rust truncates, Swift
  rounds, and 7+ fractional digits cannot be made byte-identical): a documented
  limit rather than a bug to chase. It binds tests too — a round-trip test that
  asserted bit-exact `f64` equality failed for this reason and was corrected to a
  tolerance, which is the honest assertion.

  Every DISCRETE field — level, band, glyph, unit, counts, datetimes, strings —
  round-trips exactly, and those are what clients branch on.

## Wire types

Every route is a READ. Banshee's writer is a timer, not a person — the sampler
owns every insert — so there are no request bodies below, and the whole surface is
"stored state, projected onto the wire".

| Route | CLI | MCP tool | Body |
|---|---|---|---|
| `GET /health` | `banshee health` | `health` | `{status, version}` |
| `GET /pressure` | `banshee status` | `pressure` | `Pressure` |
| `GET /headroom` | `banshee headroom` | `headroom` | `Headroom` — the verdict reduced to a decision for agents (ADR-0010) |
| `GET /samples` | `banshee samples` | `samples` | `[Sample]`, oldest first (last 24h) |
| `GET /rollups` | `banshee rollups` | `rollups` | `[Rollup]`, oldest first (5-min buckets, 30 days) |
| `GET /census` | `banshee census` | `census` | `Census`, or 404 |
| `GET /alerts` | `banshee alerts` | `alerts` | `[AlertEpisode]`, newest first; open episodes always included |
| `GET /deltas` | `banshee deltas` | `deltas` | `Deltas` — what changed over a lookback (`?vs=1h`, default; or `?vs=episode`), composed once in core |
| `GET /stats` | `banshee stats` | `stats` | `{schemaVersion, samples, rollups, censuses, alerts, dbSizeBytes, lastEvaluatedAt, consecutiveEvalFailures, lastSweptAt, consecutiveSweepFailures, selfFootprintBytes, selfCpuSecs, selfUptimeSecs, selfCpuPercent}` |

**That table is the parity contract**, and `tests/e2e/run-e2e.sh` iterates it: each
row must exist on all three surfaces, and their bodies must be byte-identical.
Adding a route without its CLI subcommand and MCP tool fails the gate.

### Actions: the write surface

The reap actions are the ONE part of the surface that changes the machine (not
the database — they kill processes). Each exists twice: a read-only `preview`
(dry run) and a `execute`. **Preview and execute call the same candidate
selector**, so what a person approves is what runs; **execute takes no
parameters**, because targets are recomputed at execution time and never accepted
from a caller (PIDs recycle — `banshee_core::actions`).

| Route | CLI | MCP tool | Body |
|---|---|---|---|
| `POST /actions/reap-stale-sessions/preview` | `banshee reap-stale-sessions` | `reap_stale_sessions_preview` | `SessionReapReport` |
| `POST /actions/reap-stale-sessions/execute` | `banshee reap-stale-sessions --execute` | `reap_stale_sessions_execute` † | `SessionReapReport` |
| `POST /actions/reap-orphans/preview` | `banshee reap-orphans` | `reap_orphans_preview` | `OrphanReapReport` |
| `POST /actions/reap-orphans/execute` | `banshee reap-orphans --execute` | `reap_orphans_execute` † | `OrphanReapReport` |

**† The two destructive `execute` MCP tools are ABSENT from `tools/list` unless
`BANSHEE_MCP_ENABLE_ACTIONS=1`** — absent, not present-and-refusing, so an agent
cannot choose (or be prompt-injected into choosing) a kill it was never offered.
The read-only `preview` tools are always present. The gate also holds on the
CALL, not only the listing. This is why the actions are NOT in the byte-identical
parity table above: the execute tools are conditionally present, and an execute
payload's `outcome` fields are not frozen. The harness's section 8 checks the
previews for cross-surface shape parity, the executes for existence and the
no-body/target-list write contract, and the MCP gate both ways — all against an
impossible census overlay so no real process is ever touched.

`SessionReapReport` is `{action, executed, tmuxAvailable, staleDays, candidates:
[SessionCandidate]}`; a `SessionCandidate` is `{session, paneCommand, idleDays,
cwd, verdict (reap|spare), reason, outcome}`. `OrphanReapReport` is `{action,
executed, termWaitSecs, candidates: [OrphanCandidate]}`; an `OrphanCandidate` is
`{pid, program, args, rssBytes, ageSecs, outcome}`. `idleDays`, `cwd` and every
`outcome` are nullable and present-as-null; `outcome` is null on a preview.
**There is deliberately no timestamp** — a report describes the call that
produced it, and a timestamp would make the payload impossible to compare across
surfaces.

### Clients relay bytes; they do not re-serialize

**A client that parses a payload and re-emits it has changed it.** Measured
2026-08-31 by the parity harness on a live census: the API served
`"cpuSecsTotal":15640.710000000001` and the CLI printed `15640.71`, because
`serde_json` reads an `f64` back one unit in the last place lower. So
`banshee <cmd> --json` and the MCP tool results pass the API's bytes through
unchanged, and pretty-printing is `jq`'s job. This binds any future client: relay,
do not round-trip. A consumer doing arithmetic on a number a client quietly altered
has no way to notice.

### Why `/samples` and `/rollups` are two routes

A rollup has `load1mAvg` and `load1mMax` where a sample has `load1m`. A single route
that returned one shape or the other depending on how old the requested window was
would be a **union type on the wire**, and every client would have to sniff which it
got before reading a field. Two routes with identical parameters is the cheaper
contract.

The split follows the retention tiers (ADR-0006): raw samples for 24 hours, and
5-minute buckets for 30 days. The two tiers OVERLAP for the last day: a bucket is
summarised as soon as it closes (the sweep runs once per bucket), so `/rollups` is
dense from the last five-minute boundary back 30 days, and the raw rows behind the
newest day's buckets are still there for `/samples`. `/samples` returns nothing for
a window older than the raw retention — deliberately, rather than silently
substituting buckets. (Until 2026-09-08 rollups were written only as samples aged
out, so `/rollups` held nothing younger than 24 h and the app's short History
windows were empty by construction.)

Neither route row-caps a WINDOW. The retention policy is the bound (5,760 samples a
day; 8,640 buckets a month), and refusing "give me the month" would refuse the one
question `/rollups` exists to answer. `limit` is capped at 500 because it is the
convenience mode, and an over-large `limit` is a 400 rather than a silent clamp.

### Pressure

The verdict. **Computed once, in `banshee-core`, and served whole — glyph
included** (ADR-0003 is about disk; the relevant one here is
[ADR-0005](adr/0005-pressure-model-in-core.md)). No client re-derives a level, a
band, a severity, a glyph, or an action's wording.

```json
{
    "evaluatedAt": "2026-08-31T15:04:05.123456Z",
    "level": "restless",
    "levelName": "Restless",
    "source": "memory",
    "glyph": "😧🧠",
    "accessibilityLabel": "Banshee: Restless, memory",
    "dimensions": [ /* DimensionReading */ ],
    "findings": [ /* Finding */ ],
    "sampleCount": 40,
    "censusCount": 3,
    "recovering": false,
    "activity": { "open": 1, "lastHour": 1, "lastDay": 3 }
}
```

| Field | Type | Nullable | Notes |
|---|---|---|---|
| `evaluatedAt` | datetime | no | canonical form |
| `level` | enum | no | `checking` \| `quiet` \| `stirring` \| `restless` \| `wailing` \| `shrieking` |
| `levelName` | string | no | the display name; render it, do not derive it |
| `source` | enum | **yes** | `cpu` \| `memory` \| `disk` \| `sprawl` \| `managedAgents`; null below `restless` |
| `glyph` | string | no | **the menu bar renders this verbatim** |
| `accessibilityLabel` | string | no | spoken by VoiceOver; words, never emoji |
| `dimensions` | array | no | `[]` when `checking`, never null |
| `findings` | array | no | `[]` when there is nothing to say |
| `sampleCount` | integer | no | samples in the evaluated window |
| `censusCount` | integer | no | censuses in the evaluated window |
| `recovering` | boolean | no | some dimension is `recovering` (ADR-0009) — see below |
| `activity` | object | no | `{open, lastHour, lastDay}`: alert episodes live now, and ACTIVE (not merely started) in the last hour / day |

**`checking` is not `quiet`.** It means the daemon has not gathered enough samples
yet, and it is the state served before the sampler's first evaluation. A client
that renders it as calm is lying at the worst possible moment; a client that
invents a `quiet` for a missing verdict is doing the same thing on purpose.

**`glyph` and `source` must agree.** A suffix is present exactly when `source` is
non-null. Note that the suffix is not always one code point — `sprawl` is 🕸️,
a spider web plus U+FE0F — so nothing may truncate a glyph by character count.

**`recovering` is a modifier, not a seventh level** (ADR-0009 decision 8). When
some dimension has dropped below red inside its alert episode's down window, the
verdict carries `recovering: true` and that dimension carries `recovering: true`;
if the machine is otherwise calm (`quiet` or `stirring`) core ALSO appends 🩹 to
the glyph and ", recovering" to the label — so "calm" and "calm, but was red a
moment ago" are different faces. At `restless` and above the glyph is left to the
source suffix. Clients render the glyph and label verbatim as always; the flags
are for the row, not for re-composing the face.

**`activity` is the long memory on every surface.** A `quiet`
verdict with `activity.lastDay: 12` describes a calm moment in a bad day; a client
that shows only the level is hiding the story `/alerts` would tell.

### Headroom

The verdict reduced to what an agent should DO ([ADR-0010](adr/0010-headroom-is-a-decision.md)):
**a decision, not a number**. Derived in `banshee-core` from the `Pressure` the
sampler just published plus the newest sample's core count, published in the same
breath, and served whole — no client re-derives a parallelism from raw numbers.
Advice, not enforcement: an agent hook built on it will return `ask`, never `deny`.

```json
{
    "evaluatedAt": "2026-09-08T23:15:00.000000Z",
    "level": "restless",
    "shouldWait": true,
    "recommendedParallelism": 0,
    "retryAfterSecs": 60,
    "cores": 8,
    "reason": "Restless: Thermal pressure is red — kernel reports heavy (held 45s). Wait; retry in 60s.",
    "conditions": [
        { "type": "Ready", "status": "True", "reason": "VerdictAvailable", "message": "40 samples, 3 censuses in the window", "since": null },
        { "type": "CpuPressure", "status": "False", "reason": "AllGreen", "message": "20% busy", "since": "2026-09-08T23:05:00.000000Z" },
        { "type": "ThermalPressure", "status": "True", "reason": "ThermalRed", "message": "kernel reports heavy", "since": "2026-09-08T23:14:15.000000Z" }
    ]
}
```

| Field | Type | Nullable | Notes |
|---|---|---|---|
| `evaluatedAt` | datetime | no | the evaluation this was derived from — the same instant as `/pressure` |
| `level` | enum | no | the verdict's level; `checking` ⇒ `shouldWait: true` (headroom is never invented before data) |
| `shouldWait` | boolean | no | do not start new work now. **Exactly `recommendedParallelism == 0`** |
| `recommendedParallelism` | integer | no | how many MORE concurrent CPU-bound workers the machine can absorb right now |
| `retryAfterSecs` | integer | **yes** | seconds before asking again; **present exactly when `shouldWait`**, null otherwise |
| `cores` | integer | **yes** | the core count the arithmetic used (newest sample's `ncpu`); null before the first sample |
| `reason` | string | no | one sentence, composed in core — quote it verbatim |
| `conditions` | array | no | always 7: `Ready`, then `CpuPressure`, `MemoryPressure`, `ThermalPressure`, `DiskPressure`, `SprawlPressure`, `ManagedAgentsPressure`, in that order |

**Condition** (Kubernetes node-condition shape — note the key is `type`, not `kind`,
and the statuses are spelled `True` / `False` / `Unknown` as Kubernetes spells them):

| Field | Type | Nullable | Notes |
|---|---|---|---|
| `type` | string | no | `Ready`, or `<Source>Pressure` |
| `status` | enum | no | `True` (a red on that source) \| `False` (a reading, nothing red) \| `Unknown` (no reading yet — no census, a pre-v11 thermal column). For `Ready`, `True` means the verdict is trustworthy |
| `reason` | string | no | CamelCase token: the worst dimension and its band (`SwapRed`, `CpuYellow`), or `AllGreen`, `NoReading`, `VerdictAvailable`, `Checking`. Stable; branch on it |
| `message` | string | no | that dimension's `detail` from the verdict, verbatim |
| `since` | datetime | **yes** | when the worst dimension entered its band (`evaluatedAt − heldSecs`, so a gap in observation truncates it); null when `Unknown`, and always null for `Ready` |

**Polarity.** Like Kubernetes, `<Source>Pressure: True` is bad news and
`Ready: True` is good news. A yellow band is `False` with a reason that says so
(`SwapYellow`) — visible without being an alarm. Advisory dimensions (uptime) never
appear in a condition.

**The formula** (ADR-0010 decision 5; the defaults are configuration in
`PressureConfig.headroom_*`): slots = min(free cores from the CPU reading,
(available memory − 25% of total RAM) ÷ 2 GiB), capped by level (Quiet all cores,
Stirring half, Restless a quarter), halved at thermal MODERATE; zero and wait at
Wailing or worse, or on ANY red memory/thermal/disk dimension; floor of one
otherwise. The 25% hold-back is the OS's and the human's share; the 2 GiB budget is
a coding-agent worker plus the build it spawns (both decided on prior art, see the
ADR).
`retryAfterSecs` is a fixed ladder: 30 (checking), 60 (a red below Wailing), 120
(Wailing), 300 (Shrieking). Every one of those numbers is a wire contract, and
`tests/fixtures/headroom-*.json` pin them in both languages.

### DimensionReading

```json
{
    "dimension": "swap",
    "key": "swap",
    "label": "Swap in use",
    "band": "red",
    "value": 35600000000.0,
    "unit": "bytes",
    "severity": 3.95,
    "heldSecs": 3600,
    "trendPerSec": 1235000.0,
    "detail": "35.6 GB in use, climbing 74 MB/min",
    "advisory": false,
    "pending": null,
    "recovering": false
}
```

| Field | Type | Nullable | Notes |
|---|---|---|---|
| `dimension`, `key` | enum/string | no | `cpu`, `memory`, `swap`, `kernelPressure`, `thrash`, `agents`, `orphans`, `managedAgents`, `disk`, `uptime` |
| `label` | string | no | composed in core, so every surface says the same words |
| `band` | enum | no | `green` \| `yellow` \| `red`, **after hysteresis** |
| `value` | number | no | the newest reading, in `unit` |
| `unit` | enum | no | `ratio` \| `bytes` \| `perSecond` \| `count` \| `percent` \| `days` |
| `severity` | number | no | 0.0 at yellow, 1.0 at red, negative when green; comparable ACROSS dimensions |
| `heldSecs` | integer | no | how long this band has held, counting back only as far as the observations are CONTINUOUS |
| `observationGapSecs` | integer | **yes** | the gap in observations that cut `heldSecs` short, when one did |
| `trendPerSec` | number | **yes** | null when a trend is not meaningful (a single point) |
| `detail` | string | no | human phrasing, composed in core |
| `advisory` | boolean | no | advisory dimensions produce findings but never drive the level |
| `pending` | enum | **yes** | a band the newest values imply but which is unconfirmed |
| `recovering` | boolean | no | below red inside an open episode's down window — the one green worth showing |

**`band` is not a function of `severity`.** They co-vary most of the time and come
apart exactly where it matters: a dimension recovering from red keeps its red band
until it clears the hysteresis margin, so its severity can be below 1.0 while its
band is still `red`. Branch on `band`.

**`heldSecs` is continuous-observation time, not wall-clock time.** It counts back
from now only as far as the samples are unbroken; a gap ends the run and appears in
`observationGapSecs`. That distinction is load-bearing, because `heldSecs` is what
decides whether a red is *sustained* — and a client that presents `heldSecs: 45,
observationGapSecs: 1029` as "red for 17 minutes" has reintroduced the bug:

> Minutes after the daemon was first installed (2026-09-01), a 17-minute hole
> between two samples and four more made every red dimension report `held 17m`
> off 45 seconds of observation, and the verdict was a false 💀 Shrieking. Every
> daemon restart and every laptop wake leaves such a gap by design, so the gap is
> now reported rather than absorbed.

`trendPerSec` is fitted over the trailing contiguous run for the same reason: a line
through two clusters either side of a hole describes the hole. That slope produces
the disk dimension's "full in N hours", which is the most actionable sentence the
app emits.

### Finding

```json
{
    "dimension": "swap",
    "band": "red",
    "message": "35.6 GB of swap in use.",
    "action": "relaunchApps",
    "actionLabel": "Quit and relaunch the biggest apps",
    "who": [
        { "name": "Chrome", "count": 115, "detail": "7.7 GB" },
        { "name": "claude", "count": 8, "detail": "2.1 GB" }
    ],
    "whoLine": "who: Chrome ×115 at 7.7 GB, claude ×8 at 2.1 GB"
}
```

`action` is one of `reapStaleSessions`, `reapOrphans`, `relaunchApps`, `reboot`,
`openDiskTool`, `none`. **`actionLabel` carries the wording** for the same reason
the glyph does: a client that switched on `action` to pick a string would be a
Swift table kept in step with a Rust one by hand, and a new variant would render as
blank text in whichever client forgot a case. Findings arrive already ranked by
MEASURED impact; **do not re-sort them.**

**`who` names the top consumers behind the finding**, biggest first, from
the daemon's own process census — at most `who_limit` (3) of them, each with the
census's `name` for the group, its process `count`, and its cost as a worded
`detail` in the dimension's own terms. **`whoLine` is the same list as one
sentence, composed in core; render it verbatim.** It is `null` exactly when `who`
is empty — disk and uptime have no process behind them (ADR-0003), a finding
built before the first census names nobody, and the Shrieking reboot finding
names nobody because the swap finding above it already did. Both keys are always
present. The attribution rules live in one place
(`rust/banshee-core/src/pressure/who.rs`) and are not obvious enough to
re-derive client-side: memory, swap, kernel pressure and thrash rank by RESIDENT
size; CPU and thermal by the census's cumulative-CPU rule (Σ CPU seconds over the
group's longest lifetime — a sustained rate, not an instantaneous `%CPU`), with
the managed agents as ONE deduplicated entry and any group younger than
`managed_agents_min_life_secs` skipped; stale sessions by the RSS reaping them frees;
orphans by the census's per-program breakdown. A daemon from before the who-line
existed sends neither key; clients decode that as "names nobody".

### Sample, Census, AlertEpisode

Large, mechanical, and pinned twice rather than transcribed here — a field table
for `Census` would be forty rows that drift. The parity harness pins them
cross-SURFACE on live bytes; the shared fixtures (`samples.json`, `rollups.json`,
`census-full.json`, `stats.json`, `alert-episode.json`) pin them cross-LANGUAGE,
decoded by both unit suites. What binds:

- **`Sample`** is one cheap-tier reading: `id`, `sampledAt`, `bootTimeSecs`,
  `load1m`/`load5m`/`load15m`, the `pages*` counters, `swapins`/`swapouts`, and a
  `volumes` array of `{mountPoint, totalBytes, availBytes}`. `bootTimeSecs` is the
  reboot discriminator: two samples with different values have **no valid counter
  delta between them**, so a consumer computing a rate must check it.
  **`pagesFree` is not availability** (schema v7): available
  memory is `pagesFree + pagesSpeculative + pagesPurgeable + pagesExternal`,
  times `pageSize`. macOS keeps the free list deliberately tiny, so a consumer
  banding or alerting on `pagesFree` alone reproduces the false-Shrieking-class
  bug the memory dimension shipped with.
  **`thermalPressureLevel`** and **`cpuSpeedLimitPercent`** (schema v11) are
  BOTH nullable and present-as-null: the kernel's thermal enum (0 nominal … 4
  sleeping — 0 is a real reading, so "not recorded" has to be null, not 0) and
  IOKit's CPU speed limit percent, which Apple silicon does not publish (null on
  every modern Mac; Intel only). A pre-v11 daemon omits the keys; clients decode
  them as optional.
  **`memoryPressureLevel`** (schema v8) is the kernel's own
  verdict, `kern.memorystatus_vm_pressure_level`: 1 normal, 2 warn, 4 critical —
  and **0 means a pre-v8 row never recorded it**, which a consumer must treat as
  "unknown", never as "normal". It feeds the `kernelPressure` dimension.
- **`Census`** is the 5-minute reading: `agentSessions`, `ideHelpers`, `orphans`,
  `tmuxSessions`, `appGroups`, `monitorAgents`, and `monitorTotal`.
  **`tmuxAvailable: false` is not "zero sessions"** — it means the census could not
  look, and a UI that conflates them reports a clean machine. And **never sum the
  per-agent `percentOfOneCore` values**: each divides by the longest-lived process
  in its own group, so the denominators differ (a real census summed to 59.9%
  against an honest 49.2%). `monitorTotal.percentOfOneCore` is the deduplicated
  figure.
- **`Rollup`** is one 5-minute bucket: `bucketStart`, `sampleCount`, and then
  AVERAGES AND MAXIMA where a sample has a reading — `load1mAvg`/`load1mMax`,
  `swapUsedAvg`/`swapUsedMax`, `pagesFreeMin`, `pagesCompressorMax` — plus a
  `volumes` array of `{mountPoint, totalBytes, availMin, availAvg}`.
  `swapinsDelta`/`swapoutsDelta` are INCREASES across the bucket and are **null when
  a reboot inside it voided the counters — null is not zero.** A client that renders
  the void as `0` reports a calm five minutes that was never observed.
  `pagesFreeMin` is in PAGES; the page size lives on the raw sample, not here.
  **The census scalars** (schema v9): `staleSessionsMax`,
  `orphansMax`, `monitorPercentMax` (the deduplicated figure — never a sum of
  per-agent rows), `totalProcsMax` — the month-scale sprawl trend, folded in by
  the retention sweep before the censuses themselves age out. **Null means no
  census fell in the bucket (or the rollup pre-dates v9) — the same
  null-is-not-zero rule as the deltas.**
- **`AlertEpisode`** (ADR-0009) is one continuous incident on one dimension:
  `{id, dimension, startedAt, endedAt, peak{band, level, severity, at, message},
  suppressed, state, lastNotifiedAt, recoveringSince}`. `state` is `firing` |
  `recovering` | `closed` and is carried rather than derived. **`endedAt: null`
  means STILL OPEN** — present as null, never absent — and open episodes are served
  by `/alerts` whatever `since` says. `peak` is the worst moment (level first, then
  severity), its `message` is the finding's wording at that moment, and its
  `whoLine` is the finding's who-line at that moment — null when the
  finding named nobody and for episodes recorded before the line existed.
  Notification text is `<finding message> Red for <duration>; <whoLine>.` — the
  same words as the worklist, then how long, then who, re-read from the CURRENT
  finding on every notice so a repeat names who is behind it now.
  **`suppressed` is the count of re-fires the episode absorbed** inside the repeat
  interval, each of which the pre-v10 point-event model would have rate-limited
  away without a trace: `39` is forty storms, `0` is one. Render it as "+N more".
  `lastNotifiedAt` is null when every notice so far was inhibited (a firing
  `thrash` episode mutes `memory`'s notices, not its episode). Pre-v10
  `alert_events` rows are NOT backfilled — the record starts at the upgrade.
  **`censusAtPeak`** is a compact `CensusSummary` of who was running at the
  worst moment — `{takenAt, totalProcs, consumers[{name, kind, count, rssBytes}],
  orphanCount, monitorPercentOfOneCore}`, biggest consumer first. It moves WITH
  the peak and only with the peak, so it answers "who was behind this" for the
  incident, not the newest tick. **Present-as-null and defaulted**: no schema
  change, so an episode recorded before deltas existed simply has no `censusAtPeak` — Rust reads it via
  `#[serde(default)]`, Swift via `decodeIfPresent`, both to null.
- **`Stats`** adds sampler operational health: `lastEvaluatedAt`
  and `lastSweptAt` (nullable, canonical datetime — present-as-null before the
  first run), and `consecutiveEvalFailures` / `consecutiveSweepFailures`. A
  frozen `lastEvaluatedAt` or a rising eval-failure count means the served
  verdict is going stale; a rising sweep-failure count means the row count is no
  longer bounded (ADR-0006).
- **`Stats`** also says what Banshee ITSELF costs:
  `selfFootprintBytes` (the daemon's physical footprint — Activity Monitor's
  "Memory", not RSS, which falls on a swapping machine while the real cost does
  not), `selfCpuSecs` (cumulative user+system CPU since the process started),
  `selfUptimeSecs` (FRACTIONAL seconds since start, so the percent can be
  recomputed from the same payload even in the daemon's first second) and
  `selfCpuPercent` (the
  lifetime average `cpu / uptime × 100`, one core = 100). The percent is a
  reduction and is served, not re-derived (ADR-0005); the raw figures ride
  beside it so nothing is hidden. A client seeing an older daemon (fields
  absent) must render "—", never a claim of zero cost.

### Deltas

`Deltas` answers "what changed" over a lookback, composed ONCE in core as
a pure function of stored history — the human sentence too, so no surface words it
itself (ADR-0005). `{evaluatedAt, lookback, episodeId, requestedLookbackSecs,
anchorAt, actualLookbackSecs, verdict{thenLevel, nowLevel, thenSource, nowSource,
detail}, dimensions[{dimension, key, label, unit, then, now, delta, thenAt, nowAt,
observationGapSecs, detail}], consumers[{name, kind, thenCount, nowCount,
thenBytes, nowBytes, deltaBytes, detail}], census{thenAt, nowAt}, observationGapSecs,
summary}`. What binds:

- **Ranked by CHANGE, not size.** `consumers` sorts by `|deltaBytes|` descending,
  so the thing that MOVED leads even when a larger thing sat still — the opposite
  of the who-line's ranking. Chrome at 8 GB that freed 4 GB outranks claude that
  grew 0.6 GB outranks the 8 GB that did not budge.
- **A gap is never absorbed.** `observationGapSecs` rides the top AND every
  dimension, present-as-null: it is the largest hole between the anchor and now.
  When set, the `summary` says the arithmetic "spans a hole" — because a delta
  over an unobserved gap is arithmetic on a hole, and on macOS "used memory went
  down" is not "pressure went down" (the same `held_secs` hazard as the gap rule above).
- **`consumers` and `census` travel together.** Both need two censuses in reach;
  when there are not, `consumers` is `[]` and `census` is null (present, not
  absent) — the delta is dimensions-only, still honest.
- **The lookback is echoed as asked.** `lookback` is the label (`"1h"`,
  `"episode"`); `requestedLookbackSecs` vs `actualLookbackSecs` diverge when the
  history was shorter than the ask, and the `summary` says "asked for …". `vs`
  over the raw retention is a 400, never a silent clamp.
- **`vs=episode`** anchors against the episode's stored `censusAtPeak` and sets
  `episodeId` (lowercased UUID), tying the two halves together: the record's peak
  answers "what changed since this began" even after the live censuses behind it
  are swept.

The three shared fixtures (`deltas-normal.json`, `deltas-gap.json`,
`deltas-episode.json`) pin all of this cross-language; the parity harness pins it
cross-surface on live bytes.

### Query parameters

| Route | Parameter | Notes |
|---|---|---|
| `/deltas` | `vs` | the lookback: a duration (`90s`, `30m`, `1h`, `24h`, or bare seconds) or the literal `episode`. Defaults to `1h`. Below one minute (cannot hold two samples) or above the raw retention is a **400, never a silent clamp**. |
| `/samples` | `limit` | 1–500. **Over the ceiling is a 400, not a silent clamp** — an agent that asks for 5,000 and receives 500 without being told reasons about a window it did not get. |
| `/samples` | `from`, `to` | ISO-8601 UTC; half-open `[from, to)` so adjacent windows tile. `to` requires `from`; combining either with `limit` is a 400. |
| `/rollups` | `limit`, `from`, `to` | **Identical semantics to `/samples`**, deliberately: one thing to learn. Default `limit` 60 buckets (five hours). |
| `/alerts` | `since` | defaults to 24 hours ago; matched against `startedAt`, and OPEN episodes are included regardless |
| `/alerts` | `limit` | 1–500; a capped read drops the OLDEST |

Datetime parameters go through the **generous** decoder, so every producer in the
table above is accepted on the way in even though only the canonical form is
emitted. Unknown query parameters are **ignored** on a read — the opposite of the
write-DTO rule below, and deliberately: a stray `?foo=1` is harmless, whereas a
misspelled field on a write silently loses data.

### Error shape (all non-2xx responses)

```json
{"error": "limit must be between 1 and 500"}
```

**"All" is literal — there is no escape hatch.** Framework-generated rejections
leak `text/plain` by default and MUST be re-clothed in this shape: bad query value
(400), unmatched route (404), wrong method (405), and — **when a write route or a
path parameter first appears** — unknown-field / malformed-body (422) and
malformed-path-param (400). A `text/plain` body here is the worst agent-first bug
in the stack: the CLI and MCP server both do `resp.json()`, so a non-JSON error is
destroyed into "invalid JSON from API" and the agent loses the one recovery signal
it needed (see `rust/banshee-api/src/routes.rs` for the wrapper extractor +
response fallback).

> **Obligation, half discharged.** The first write routes — `/actions/*` —
> brought the `Json<T>` wrapper back as `ApiJson<T>` in `routes.rs`: a malformed
> or unexpected-field execute body is now a `422 {error}`, not stock `text/plain`,
> and a caller-supplied target list is refused by name rather than silently
> ignored. Pinned by `an_execute_body_is_optional_but_never_a_target_list` and by
> the e2e harness's section 8. **`Path<T>` is still owed by the first route with a
> path parameter** — none exists yet, so the wrapper stays out rather than sitting
> as dead code guarding a contract nothing exercises.
